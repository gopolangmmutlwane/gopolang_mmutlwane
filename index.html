1.1 / How I approach the work

A model is an answer.
The investigation is the work.

I try to keep the reasoning visible. Before a model, I investigate the data. During modelling, I test assumptions and appropriate metrics. Afterwards, I ask whether the result actually solves the original problem.

Question→ Investigate→ Build→ Validate→ Interpret
•

Question the data.

Before modelling, I look for leakage, missing information, unusual observations, class imbalance and relationships that could distort the result. On one project that meant catching identifier leakage and a multicollinearity bug that was flipping a coefficient's sign before it ever reached the accuracy score.

•

Test the claim.

Accuracy is only one piece of evidence. Depending on the problem, I look at precision, recall, F1, error patterns, validation behaviour and whether the result makes sense in context, measured in terms that actually matter: Rand of business impact, recall on the minority class, whether two clustering methods actually agree.

•

Understand the failure.

A model that performs well in a notebook but fails when the data changes isn't a successful solution. When segment and default risk didn't meaningfully correlate on one project, that finding shaped the final recommendation instead of getting buried. Not every analysis needs to confirm the original hypothesis.

•

Communicate the finding.

The objective isn't to produce the most complicated model. It is to turn analysis into something another person can understand, question and use.

01 / THUSO BANK PIPELINE REBUILT

When a model looks better than it really is.

Credit-risk neural network + leakage investigation.

A credit-risk neural network initially appeared to perform strongly. Investigation revealed identifier leakage, making the original evaluation unreliable, so the pipeline was rebuilt and re-evaluated using evidence beyond a single accuracy score.

0.774 ROC-AUC0.61 default recall
Neural NetworksCredit RiskLeakage DetectionSHAP
View on GitHub →

Thuso Bank needed a loan default model that could withstand scrutiny under South Africa's National Credit Act, which requires lenders to justify credit declines, and POPIA's restrictions on automated decisions. The starting point was deliberately broken production code.

Diagnosis

  • Customer ID fed into the model as a feature
  • Ordinal encoding applied to nominal categories
  • Wrong loss function for the classification task
  • No regularisation or imbalance handling on an eleven percent default rate

Fix

  • Identifier column dropped from the feature set
  • Correct categorical encoding applied
  • Loss function matched to the classification task
  • Regularisation and class imbalance handling added

View on GitHub →

Compared Logistic Regression, SVM, and a Decision Tree to flag likely e-commerce purchasers mid-session, against 84.5 percent class imbalance and a five-fold cross-validation check on the winning model.

Why not one model

  • 84.5% class imbalance made a single algorithm's accuracy score unreliable alone
  • No single model type reliably outperforms across all purchase-intent session patterns

Approach

  • Logistic Regression, SVM, and a Decision Tree each evaluated under five-fold cross-validation
  • F1 on the purchase class, not raw accuracy, decided the winner
